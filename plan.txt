## Part 1: The Four BEPs in Detail

### BEP 10 — Extension Protocol (LTEP)

This BEP doesn't do anything useful on its own — it's a *dispatch mechanism* that lets two peers negotiate which optional extensions they both support, without breaking compatibility with clients that don't know about extensions at all.

**How it works:**
- One of the 8 reserved bytes in the handshake (`reserved[5]`, using bit `0x10`) signals "I support the extension protocol."
- A new peer-wire message ID, `20` (`Extended`), is reserved for *all* extension traffic. Its payload format is: `<extended-message-id: 1 byte><payload>`.
- `extended-message-id = 0` is special — it's the **handshake message**, a bencoded dict sent right after the normal 68-byte handshake:
  ```
  {
    "m": {"ut_pex": 1, "ut_metadata": 2},
    "p": 6881,
    "v": "MyClient 1.0",
    "yourip": "<binary IP>",
    "reqq": 250,
    "metadata_size": 34567
  }
  ```
  - `"m"` maps extension names to message IDs *that peer* wants to use for them. Each peer picks its own IDs independently, so you have to keep a per-connection lookup table (e.g. peer A calls PEX "1", peer B calls it "3").
  - `"metadata_size"`, `"p"`, `"v"`, `"yourip"` are optional informational fields other extensions rely on.

**Why it matters:** every extension (PEX, ut_metadata, holepunch, etc.) is just a new entry in that `"m"` dict plus a new bencoded message format riding on message ID 20. Once you have the handshake and the ID-dispatch table working, adding a new extension is just "parse this dict, do something with it."

In your code, this touches `Handshake::reserved` in `inc/peer_wire/peer_message.h` (currently always zero) and would add a new case to the `MessageId` enum plus a per-`PeerConnection` map of extension-name → id.

### BEP 11 — PEX (`ut_pex`)

**Purpose:** let two already-connected peers tell each other about *other* peers they know for the same torrent, without going through the tracker or DHT. It's cheap, low-latency, and reduces load on trackers/DHT.

**Mechanics:**
- Runs as an extension message (name `"ut_pex"`) negotiated via BEP 10.
- Periodically (typically every 60s, and not on every single connect/disconnect event), each peer sends a bencoded dict:
  ```
  {
    "added": "<compact peer list, 6 bytes each: 4-byte IP + 2-byte port>",
    "added.f": "<1 flag byte per peer in 'added'>",
    "dropped": "<compact peer list, peers disconnected since last message>"
  }
  ```
- The `added.f` flags are worth knowing about: bit `0x01` = peer prefers encryption, `0x02` = peer is a seed, `0x04` = peer supports uTP, `0x08` = peer supports holepunch (BEP 55), `0x10` = this was an outgoing connection for the sender. Notice bit `0x04` — **PEX is actually how uTP support gets advertised to peers**, so PEX and uTP aren't fully independent.
- You need to track deltas per-peer-connection (who did I just add/drop since the last PEX message to *this specific peer*), and cap the number of peers sent per message (usually ~50) to avoid abuse.

**Why it's cheap for you specifically:** you already have compact peer address encode/decode logic from DHT (nodes are exchanged in the same "4 bytes IP + 2 bytes port" compact format), and you already have a peer address type (`inc/peer_address.h`). PEX just reuses that serialization and adds delta-tracking bookkeeping to `PeerConnection`/`TorrentManager`.

### BEP 9 — ut_metadata

**Purpose:** lets a client that only has an info-hash (i.e., a magnet link, with no `.torrent` file) download the actual metadata (`info` dict) from peers who already have it. This is the missing piece that makes magnet links work at all — right now your README mentions magnet-link support as a goal, but there's no metadata-fetch path in the code.

**Mechanics:**
- Extension name `"ut_metadata"`, negotiated via BEP 10. Peers who *have* the full metadata advertise `"metadata_size"` in their extension handshake.
- Metadata is chopped into fixed 16 KiB (16384-byte) blocks. If `metadata_size` isn't a multiple of 16384, the last block is just shorter.
- Three message types, sent as a bencoded dict as the message body (for `data`, raw bytes are appended *after* the bencoded dict, not inside it):
  - `msg_type: 0` (**request**) — `{"msg_type": 0, "piece": <index>}`
  - `msg_type: 1` (**data**) — `{"msg_type": 1, "piece": <index>, "total_size": <bytes>}` followed by the raw 16 KiB chunk
  - `msg_type: 2` (**reject**) — peer doesn't have this piece (yet) or is throttling you
- Client logic: once you know `metadata_size` from any peer, allocate a buffer, request each piece index in turn (from one or several peers), reassemble, then SHA-1 hash the whole thing and confirm it matches the info-hash from the magnet link before trusting it (since any peer could send garbage).
- Once metadata is verified, you effectively "materialize" a normal `.torrent` info dict and hand off to your existing piece-manager/disk-writer path — no other code needs to change downstream.

**Why it's cheap once BEP 10 exists:** the request/data/reject exchange is a trivial extra message type; the only real new work is the "torrent has no metadata yet" state in your `TorrentManager` (added from a magnet URI rather than a parsed `.torrent` file) and the reassembly/verification logic.

### BEP 29 — uTP (Micro Transport Protocol)

**Purpose:** a UDP-based transport, built on **LEDBAT** (RFC 6817) congestion control, designed to be "background" traffic that backs off *before* it causes bufferbloat/congestion on a typical home router — unlike TCP, which will happily saturate the link and make everything else (VoIP, browsing) laggy. This is the actual "µTorrent transport protocol" most people mean by that phrase.

**Mechanics (this is the expensive part):**
- Runs entirely over a UDP socket you already own — no OS-level "connection," so you must implement, yourself, everything TCP normally gives for free:
  - **Connection setup/teardown**: packet types `ST_SYN`, `ST_STATE`, `ST_FIN`, `ST_RESET`, `ST_DATA`, tracked by a 16-bit connection ID.
  - **Reliable, ordered delivery**: sequence numbers, cumulative + selective ACKs (SACK extension header), retransmission timers derived from an RTT estimator.
  - **Congestion/flow control**: LEDBAT measures one-way delay (not just packet loss like TCP) to detect a growing queue *before* it causes drops, then throttles proactively. This needs its own delay-history tracking and window computation, separate from your peer-wire logic.
- Because it's a fundamentally different transport, your `peer_connection.cpp` would need an abstraction so it can sit on top of either your existing `Socket`/`SslSocket` (TCP) or a new `UtpSocket` — the peer-wire protocol layer (handshake, choke/unchoke/have/request/piece) stays identical either way, only the byte-transport underneath changes.
- Bonus: uTP can share the *same* UDP port your DHT already uses, which is good for NAT traversal (only one UDP hole needs to stay open) — but this is also why it's a bigger lift: you'd be multiplexing DHT KRPC traffic and uTP data traffic on one socket, demultiplexed by packet format.

**Why last:** it's valuable (NAT traversal, no bufferbloat) but architecturally independent from BEP 10/11/9 — it doesn't unblock or get unblocked by them, and it's the single largest chunk of new code (essentially reimplementing a mini-TCP). Doing it last means you get PEX + magnet links working quickly, then tackle the harder transport work without time pressure.

## Part 2: What I'd Consider the Full Feature Set for a Serious BitTorrent Client

Ignoring your `plan.txt` ordering, here's how I'd bucket everything a client "should" eventually have, roughly in order of how load-bearing they are to the core experience:

### Tier 1 — Protocol fundamentals (you mostly have these)
- Bencode parsing/encoding — done
- `.torrent` parsing, multi-file torrents — done
- Peer wire protocol core messages (handshake, choke/unchoke/interested, have, bitfield, request/piece/cancel) — done
- Piece/block-level disk I/O with hash verification — done (`disk_writer`, `piece_manager`)
- HTTP + UDP tracker support, multi-tracker tiers (BEP 12) — HTTP/UDP done; check if tiers/fallback-on-failure across tracker groups is handled
- DHT (BEP 5) for trackerless peer discovery — done
- UPnP/NAT-PMP port mapping — UPnP done

### Tier 2 — Extension-protocol family (your immediate next steps)
- BEP 10 Extension Protocol — missing
- BEP 11 PEX — missing
- BEP 9 ut_metadata (magnet link support) — missing
- BEP 6 Fast Extension (`Have All`/`Have None`, `Allowed Fast`, `Suggest Piece`, `Reject Request`) — reduces handshake chatter and lets seeds skip sending a giant bitfield; cheap add once you're touching message dispatch anyway

### Tier 3 — Peer-selection algorithms (this is where BitTorrent's efficiency actually comes from)
- **Choking algorithm**: tit-for-tat reciprocation + periodic "optimistic unchoke" of a random peer — this is the actual incentive mechanism that makes BitTorrent swarms self-organizing and fair. Worth prioritizing even before PEX if it's not there yet, since without it you're likely just unchoking everyone or nobody.
- **Piece-picking strategy**: rarest-first for the bulk of the download, randomized for the first piece, "endgame mode" (request the last few pieces from multiple peers simultaneously to avoid one slow peer stalling completion)
- Connection limits (global + per-torrent) and peer prioritization when you have more known peers than connection slots
- Upload/download rate limiting (global and per-torrent)

### Tier 4 — Session/storage robustness
- **Fast resume**: persist download state (bitfield, partial pieces, file allocation) across restarts so you don't re-hash the whole torrent every time
- Selective file download for multi-file torrents (skip files you don't want)
- Sparse-file allocation vs. full preallocation as a user-configurable choice
- Existing-data verification when adding a torrent pointed at already-downloaded files

### Tier 5 — Security/traffic-shaping
- **Message Stream Encryption (MSE/PE)** — obfuscates peer-wire traffic so ISPs doing deep-packet-inspection can't throttle BitTorrent specifically; increasingly closer to "expected" than optional
- Strict input validation everywhere you parse untrusted network data (bencode from peers/trackers, DHT KRPC messages) — malformed or adversarial data is a real attack surface, worth an explicit audit pass
- IP blocklist support

### Tier 6 — Nice-to-have / advanced
- **BEP 19 WebSeeding** — you already flagged this in the README; lets you fetch pieces from an HTTP mirror, useful for bootstrapping cold swarms
- **BEP 14 Local Peer Discovery** — multicast on the LAN to find peers on the same network instantly, no tracker/DHT round-trip needed
- **BEP 55 Holepunch** — helps two NAT'd peers connect via a third mutually-reachable peer (ties into the PEX flag byte mentioned above)
- **BEP 52 BitTorrent v2 / hybrid torrents** — per-file Merkle-tree hashing instead of one hash per torrent; more modern but a genuinely large format change, probably not worth it unless you specifically want v2 compatibility
- Sequential/streaming download mode (useful if you ever want "play while downloading")
- A management surface — even a minimal RPC/HTTP API or CLI status is what turns this from a proof-of-concept into a daemon someone can actually run unattended (watch-folder for auto-adding torrents, ratio tracking, ETA/speed stats — you already have some of this via `SessionManager`'s status refresh)

If I had to compress this into "what would I do next, ignoring the plan file": **Tier 2 (extension protocol → PEX → magnet links)** first since it's fast and unlocks a headline feature (magnet links) your README already promises, then **choking algorithm + piece-picking strategy** if those aren't already solid (this is the part that most affects real-world download speed and swarm fairness), then MSE encryption, then uTP as the big transport project.
